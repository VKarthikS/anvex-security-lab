# ANVEX Demo Script

A 15-minute classroom walkthrough for two laptops. Everything shown on screen comes from the running services; nothing is simulated inside the UI.

## Cast

| Role | Machine | URL |
|---|---|---|
| Defender console | Laptop 1 | `http://127.0.0.1:8080` (also reachable from Laptop 2 at the LAN address) |
| Simulator station | Laptop 2 | `http://127.0.0.1:8081` |
| Traffic generator | Laptop 2 | sends real HTTP logins to the defender |

## Before the class

1. Build once: `.\mvnw.cmd clean package` (or copy a release archive from section 8 of `docs/OPERATIONS.md`).
2. Laptop 1: `java -jar defender\anvex-defender.jar`.
3. Laptop 2: `java -jar simulator\anvex-simulator.jar`.
4. Laptop 2 → *Target*: enter the Laptop 1 LAN address (e.g. `http://192.168.1.50:8080`) and press **Test handshake**. A green “ANVEX 1.0.0 handshake accepted” is required before the demo.
5. Laptop 1 → *Settings*: confirm protection is **OFF** (observation mode) before starting.

## 1. The honest baseline (2 min)

Open the defender *Monitor* on Laptop 1.

Say: *“Nothing is happening. This is the real state of the system — zero traffic, zero alerts. The dashboard never invents activity.”*

Point at the pipeline health block: telemetry queue depth, critical queue depth, worker state.

## 2. Observation mode — detect without blocking (4 min)

On Laptop 2 open *Scenario* → **Repeated guessing**, rate 2/s, duration 12 s, targets `asha.raman` and `rohan.mehta` → **Start run**.

On Laptop 1 watch the *Monitor*:

* the live activity ribbon fills with `Login request` and `Source blocked`-style entries (in OFF mode the entries are observations, not blocks);
* the traffic split shows *incoming* vs *reached authentication*;
* the event-rate sparkline rises for the duration of the run and returns to zero.

Then open *Evidence* and open the newest decision. Walk through it:

* which rule matched and its exact threshold and window;
* the observed count against the threshold;
* the policy version and the protection mode at decision time;
* the action taken (`OBSERVATION_ONLY`, because protection is OFF);
* the event references that produced the decision.

Say: *“The evidence is generated by the service, not by the browser. The web page is only a viewer.”*

## 3. Repeat the same traffic with protection ON (5 min)

On Laptop 1 → *Settings* → set **Protection ON** (loopback-only by design; a remote browser gets an explicit “loopback required” notice).

On Laptop 2 → *Scenario* → **Password spraying** over 12 accounts, rate 2/s, duration 14 s → **Start run**.

On Laptop 1:

* the *Monitor* shows source blocks appearing with a countdown ring and a *protection state* banner that reads **PROTECTION ON**;
* the traffic split now shows requests that never reached password verification;
* *Sources* shows the source with its rule hits and block history;
* *Diagnostics* shows the pipeline health and the counters that justify the numbers.

Say: *“The block is scoped to one source address and expires by itself. It is not a permanent ban, and the same rule can be argued about in the evidence view.”*

## 4. Compare the two runs (2 min)

On Laptop 2 → *History*: select the first (OFF) run as baseline and the second (ON) run as candidate → **Compare**.

The report shows the measured counters from both runs and the reduction the defender actually produced, plus a label:

* `measured-comparison` — both runs completed with comparable settings;
* `small-sample` — too few requests to generalise;
* `incomplete-comparison` — one run failed or was stopped.

Say: *“These are measured numbers from this class, not a marketing claim. If a run failed, the report says so instead of hiding it.”*

## 5. Close the loop (2 min)

On Laptop 1 → *Settings* → **Unblock** the source with a note → *Monitor* shows the block cleared. Then *Reset counters* to start a clean demo, and set protection back to **OFF**.

Say: *“Everything an analyst does is itself recorded: the action, the target, the note and the time.”*

## 6. Failure modes worth showing (optional)

* Stop the defender on Laptop 1 → the simulator reports transport failures (`ConnectException`), explicitly separated from defender rejections.
* Point the simulator at a wrong port → the run is returned with `state = FAILED` and the reason, not a silent success.
* Call an analyst endpoint from a non-loopback address → `403 analyst_loopback_required` is shown as an explanation, never as a silent no-op.

## Questions that come up in class

| Question | Answer |
|---|---|
| Is the traffic real? | Yes — the simulator uses the JDK `HttpClient` against the defender over HTTP; the defender sees the Laptop 2 source address. |
| Are the demo passwords secret? | No. They are published in `docs/OPERATIONS.md` on purpose; they protect nothing but dummy accounts. |
| Does the browser decide anything? | No. Detection, protection, evidence and comparison all run in Java. The browser sends commands and renders JSON. |
| Can a remote laptop change the policy? | No. Analyst controls require a loopback caller and ignore forwarded headers. |
| Is the evidence tamper-proof? | No. It is an honest, inspectable record produced by the service, written to a local H2 database; it is a teaching artefact, not an audit product. |
| What happens when the queue fills? | The defender keeps enforcing but reports `service_overloaded` (HTTP 503) and shows the drop counters in *Diagnostics*. |
